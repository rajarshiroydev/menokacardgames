## Working agreements

- The multi-user version went live on 2026-09-25 (see the plan's decision history). Any further production data change, including the remaining ownership claims, needs the user's go-ahead in chat for that step. Development database work stays on the isolated Neon branch. Game-only changes (no database or auth change) may be released separately: backport them onto a branch from `main`, test on a Vercel preview, then push to `main` one commit at a time, with the user's go-ahead (first done 2026-09-24).
- Preserve existing game rules and flows unless a requested feature changes them.
- Look-alike UI (user decision 2026-10-27): before changing a screen or card, find its siblings reached another way (single pot and side pots, List and Table view, during and between hands, hand-by-hand and quick ledger, host and friend views) and ask the user whether each should change too. Don't change them silently, and don't leave them to later rounds.
- When the user delegates a trade-off, choose the long-term, easy-to-debug option and explain why. Ask when the choice changes behaviour the user will notice.
- Keep [`FEATURES.md`](./FEATURES.md) (plain language, for non-technical readers) updated in the same change as any user-visible behaviour, with exact numbers and limits.
- Record decisions and status in `FEATURE-PLAN.md`; record rehearsals in `MIGRATION-REHEARSALS.md`.
- Agents never see or handle secrets. The user adds secret values to `.env.local` and Vercel. Scripts may read `.env.local` but must never print values; check presence with `grep -c "^NAME="`.
- The Scoreboard UI redesign and the live standings link were released to production on 2026-09-25 (`13f9838`). The design handoff files stay untracked in `design_handoff_sporty_glass_redesign/`; the branches `ui-sporty-glass-refresh` and `live-view` are now contained in `main`.

## Confirmed product decisions

- One signed-in host owns a private friend list, games and standings. Friends are names and need no account until they sign up and link. No groups or shared ledgers. **Friend network (live since 2026-09-25):** people connect by friend request using an app-generated user code and appear in each other's friend list; a host approves every link between a login and one of their existing players; a linked person sees each linked host's standings list; no combined score across hosts. Details and build steps are in the plan.
- Ranking is average session return: the mean of `100 × (ending − invested) / invested` per eligible session, including every rebuy. Players are ranked from their first eligible session, with no provisional label, and the session count is shown. All supporting stats cover eligible sessions only.
- Sign-in is Neon Managed Better Auth with email magic links only (links expire after 5 minutes). Password sign-up and shared Google are disabled on the development and production branches; any new Neon branch needs the same check, because Neon enables them by default. Emails use Neon's shared sender by user choice.
- Rate limiting (decided 2026-10-29, audit step 4): per-account limits counted in Postgres (`lib/security/limits.ts`, migration 0033): 60 writes a minute, 120 card pictures per 10 minutes, 30 friend-code lookups per 10 minutes, 25 MB of saved games a day. Storage caps: 500 players, 5,000 games, 5 backups per account (the oldest backup is dropped). Every changing route passes `"writes"` to `requireHostAccount`; a new route must too. The one Vercel Firewall rule (Hobby allows one) becomes a backstop: all `/api/*` except `/api/live/*`, 300 a minute per IP, 429. Until the user changes it, it is still "Limit API writes" in Log mode, and it must not be switched to 429 as it is (one live host writes about 26 a minute against its 30).
- Permanent deletion of players or games requires discarding first and a sign-in within the last **10 minutes**. The user kept 10 minutes for now and may revisit it.
- Account deletion: immediate lock, hide and sign-out everywhere; recovery within **30 days**; then a daily automated purge. The disclosure quotes Neon's **6-hour** history retention, which applies to the current free plan.
- Purge infrastructure: a daily Vercel Cron job, a project-scoped Neon API key to delete the sign-in identity, and Healthchecks.io alerts.
- Starting stack must be at least 1. Since 2026-09-30 (user decision, Profile tab) each host picks a currency for the games they host; it labels every amount in their games, standings, profile and live link, and nothing is converted. Profile stats span every ledger a person played in, but the all-time net and last-10 bars add up only games in their own currency.
- People with an account go by the name they chose themselves in every host's list; only guests can be renamed (user decision 2026-09-30). Every account has its own player, tied to the account (not to a name), created automatically once it has a name; the user rejected a manual "This is me" step. An existing player becomes someone's own only by a reviewed step they confirm through `adopt_self_player` (Rajarshi's "Rajarshi" confirmed 2026-09-30; Emon's after his claim; Rahul Basak's wasn't needed, as his account name matched).
- Text case (user decision 2026-10-27): normal descriptions move from the Title Case house style (`body { text-transform: capitalize }`, since 2026-09-30) to sentence case, screen by screen, starting with the invite page (`/join`). Headings and buttons keep their style. Don't flip the body default until the user asks; write new copy in sentence case.
- Historical ownership is decided for every legacy game. Rajarshi's 27 and Rahul Basak's 2 (24, 25; 2026-10-02) are claimed in production; the Emon-led group's (32, 33, 37) are claimed when that host signs in. Never infer ownership from names or stakes; ask. Details are in [`HISTORICAL-OWNERSHIP.md`](./HISTORICAL-OWNERSHIP.md).

Give new classes a component prefix (`settings-row-danger`, `change-tag-fixed`), never a bare word, and check `app/globals.css` for an existing class first (`.danger` is a button style). Found 2026-10-05 when a "Fixed" tag became `position: fixed`.

Production data lives on `br-small-sea-ayumyssr` (named "production"; pooled host `ep-delicate-pond-ay8ple8b-pooler`), and Vercel Production connects there as `menoka_app`. Always name Neon branches by ID: a snapshot restore can swap branch names, and restores leave copies such as `restore-copy-2026-09-24` (`br-withered-glitter-ay2zbaoe`). Since 2026-09-30 Neon's default branch is production (`br-small-sea-ayumyssr`), set by the user in the console. - The app is called **Pokerize** (renamed from Menoka Card Games on 2026-10-01). The public name lives in `lib/brand.ts`; database roles, storage keys and infrastructure names keep "menoka" on purpose (plan entry "rename to Pokerize").
- Database roles: the runtime role `menoka_app` and the purge role `menoka_purge`. Both are SQL-created and unprivileged (`NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS`).
  - Roles created through Neon's role API inherit `neon_superuser` and bypass row-level security; never use them for the app.
  - Neon's console cannot reset the password of a role that has none. Set a random one in SQL first (see `migrations/README.md`).
- Migrations are applied through the Neon MCP as the owner (`run_sql_transaction`, without `BEGIN`/`COMMIT`). The owner cannot `SET ROLE menoka_app`. Test app-role behaviour with a Node script that uses `.env.local`'s `DATABASE_URL`, inside a transaction that is rolled back.
- `npm run dev` serves on port **3005**; the preview is `.claude/launch.json` → `dev`. After server-side changes, a long-running dev server can serve stale modules (for example "is not a function"); restart it.
- Next 16 allows only one `next dev` per folder. When another chat holds 3005, run a copy of the working tree (rsync without `.next`/`node_modules`, APFS-clone `node_modules`) from the scratchpad on another port, started from inside the copy (Turbopack's root is `process.cwd()`). Don't run `npm run build` in the repo while someone's `next start` uses `.next`; build in a copy.
- The in-app browser keeps its own cookies. To sign in there, the user pastes a fresh magic link into its address bar instead of clicking it in their mail client. A link must be opened in the browser that should be signed in.
- The Neon Auth SDK answers get-session from a cached cookie, so `/auth/callback` strips existing session cookies before exchanging a verifier (`lib/auth/session-cookies.ts`). Keep this whenever the SDK changes.
- Next.js 16.4.3 (since 2026-10-29, for security advisories) and `@neondatabase/auth` 0.5.0-beta are pinned. Rerun every gate after upgrading. `npm audit`'s unfixed auth SDK advisories are reviewed exceptions in `scripts/audit-exceptions.json` (review by 2026-11-30); a new high or critical one fails CI.
- **Never enable Google or any other social or OAuth sign-in on a Neon Auth branch until Neon runs better-auth 1.7.7 or later.** Magic links plus any OAuth provider allow account takeover (GHSA-965c-763c-88jm, 2026-10-27). No branch had one on 2026-10-29.
- Node 24 is pinned (`engines` and `.nvmrc`), matching Vercel's project setting; change both together. CI (`.github/workflows/ci.yml`) runs lint, `next typegen` + `tsc`, tests, build and `npm run audit:check` on every push to `main` and every pull request. It needs no secrets.
- Content Security Policy (since 2026-10-29, report-only until enforced): `proxy.ts` gives every page a policy with a fresh nonce from `lib/security/content-security-policy.ts`. Next.js puts the nonce on its own scripts and the root layout puts it on the theme script, so every page renders per request (none are static). `/csp-report` logs what the policy would block as `[csp]` lines, with tokens removed. Anything new loaded from another site (a script, image, font or API call) must be added to the policy, or it is reported, and blocked once enforced. The auth client stays off Home (loaded with `import()` when needed): its bundled `zod` probes for `eval`, which the policy reports on every load; the sign-in page still reports that once per visit, harmlessly.
- Sign-in rules (decided 2026-10-29, audit step 5): a sign-in lasts 90 days at most (`MAX_SESSION_AGE_MS`, enforced in `getHostSession`); `/admin` needs an email sign-in from the last hour; permanent deletion still needs one from the last 10 minutes. Signing out in the app backs up the game, then clears it and the live token from the phone; never clear pre-account data (`pokerLedger.v1`, `pokerLedger.history.v1`), which may exist nowhere else. Revoked sessions keep working elsewhere for up to 5 minutes (the auth SDK's `sessionDataTtl`, 300 s). Names go through `visibleText` (`lib/visible-text.ts`).
- Backups (decided 2026-10-30, until a paid Neon plan): one Neon snapshot of production, the most Neon Free allows, each with a 14-day expiry (`SNAPSHOT_KEEP_DAYS`, stated on the privacy and deletion pages). Take a new one before every production migration and whenever a session finds none (`list_snapshots`). Restore only with `finalize: false`; see `migrations/README.md`, "Backups and restore". Don't keep extra branches holding copies of production data.
- Repository (decided 2026-10-30): public on GitHub. Ruleset "Protect main" blocks force-pushes and deletion; direct pushes are fine. Dependabot: security fixes plus one grouped monthly update for npm and Actions; the Neon Auth beta and major versions stay manual. Paid items wait in `LAUNCH-AUDIT.md`, "Paid, for later".
- Monitoring (since 2026-10-29, audit step 6): Sentry (US), on only when `NEXT_PUBLIC_SENTRY_DSN` is set, so local runs, the testbed and CI send nothing. Errors only, scrubbed by `lib/monitoring/scrub.ts`; any new way an error could carry personal data must go through it. The server reports every `console.error`, so use `console.warn` for expected refusals. Security events are `[security]` lines (`lib/security/security-log.ts`). `security.txt` expires 2027-10-28; a test fails 30 days before. Sentry project `pokerize` (org `rajarshi-roy`, US). **Sentry SDK v11 ignores `sendDefaultPii`**: personal data is controlled by `dataCollection`, which defaults to collecting everything, so keep `DATA_COLLECTION` (`lib/monitoring/sentry-options.ts`) all off; a test checks it against the SDK's own list. **Sentry derives a city and country from the sender's IP at ingest even with `infer_ip: "never"` and "Prevent Storing of IP Addresses" on**; only the project's Advanced Data Scrubbing rule `[Remove] [Anything] from [$user.geo.**]` removes it (in place since 2026-10-30; Mask or another data type removes nothing). After a DSN key is reactivated, Sentry answers 403 for 2–3 minutes before accepting reports. Neither setting is reachable through the connector. Reports also drop the browser's time zone and language (`contexts.culture`), and `IGNORED_ERRORS` drops Node's process warnings, which reach the server's `console.error` capture. The uptime monitor watches `/privacy`, not `/api/health`: a database query every 5 minutes would keep Neon Free's compute awake.
- Gates: `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build`, `npm run audit:check`, plus a browser check for anything visible. CI runs all but the browser check on every push.
